# API v1 — Sync e scope

Questa pagina descrive il contratto HTTP esposto sotto `/v1` per gli errori di scope della sincronizzazione. Il literal autorevole per le entità condivise è `HOUSE_SYNC_ENTITY_TYPES` in `shared/src/contracts.ts`; non duplicare l'allowlist in client o documentazione normativa.

## Errore `sync_scope_invalid`

| Proprietà | Contratto API v1 |
|---|---|
| HTTP attuale | `409 Conflict` |
| HTTP precedente | `400 Bad Request` |
| Codice JSON | `sync_scope_invalid` (invariato) |
| Messaggio JSON | `The requested sync scope is not valid for this entity` (invariato) |
| Corpo | `{ "code": "sync_scope_invalid", "message": "The requested sync scope is not valid for this entity" }` |

Il codice descrive un'entità o una selezione di lettura incompatibile con lo scope richiesto; non dichiara che l'utente abbia perso la membership. Non cambiare scope né cancellare la coda in risposta a questo errore.

## Endpoint e condizioni

### `POST /v1/sync`

`sync_scope_invalid` è restituito quando si viola il confine tra dati personali/account e dati condivisi della casa, in particolare:

- una mutation assegna uno scope `house:<id>` a un'entità che non appartiene all'allowlist house condivisa;
- un membro corrente invia una mutation di entità condivisa nel proprio scope `account:<userId>` invece di usare l'import autenticato della coda account;
- una mutation personale usa uno scope house;
- una richiesta dichiara esplicitamente `supportedEntityTypes` incompatibili con lo scope di lettura: entità condivise nello scope account di un membro house, oppure entità personali nello scope house. Il filtro di capacità `mealPlanReadVersion` viene applicato prima della validazione e della lettura.

Per compatibilità, se `supportedEntityTypes` è omesso il server applica il set legacy di entità supportate e filtra comunque i risultati in base allo scope risolto. L'assenza del campo non è interpretata come una dichiarazione del client che account e house siano intercambiabili. La risposta non include dati di scope diversi; il filtro server-side e la verifica di membership rimangono attivi.

La validazione di stessa origine, sessione verificata e CSRF precede l'elaborazione della richiesta. `sync_scope_required` per una mutation condivisa senza scope resta `400`; una membership assente o uno scope account altrui resta `403 house_membership_required`.

### `POST /v1/house/account-queue/import`

Restituisce `sync_scope_invalid` se una mutation del batch non è condivisa secondo il contratto oppure se il suo `syncScope` non è esattamente `account:<session.userId>`. Questo endpoint è il percorso autenticato per migrare la coda condivisa account pendente quando si entra in una casa; non autorizza il client a scegliere la casa o a importare entità personali.

### `POST /v1/house/diet-profile/import`

Restituisce `sync_scope_invalid` se la mutation non è un upsert `diet_profile` per l'entità `profile`, senza `syncScope`, oppure se il payload non è un profilo dietetico valido. È il percorso esplicito per importare il profilo guest nella casa.

Anche questi endpoint richiedono stessa origine, sessione verificata e CSRF. Gli errori di forma del payload restano distinti dagli errori di scope.

## Compatibilità client

Il client web usa il codice stabile `sync_scope_invalid`, non il valore HTTP, per costruire `ApiClientError`. La coda conserva mutation e cursore finché la richiesta non ha successo; un `400` o `409` con questo codice non causa purge della casa né retag automatico dei dati. I client che non inviano `supportedEntityTypes` continuano a ricevere il feed filtrato per scope.

I client che dipendono dal solo status `400` devono migrare: leggere `code`, accettare `409` e trattare l'errore come rifiuto non retryable finché scope/mutation non sono corretti. Dettagli operativi: [`../migrations/sync-scope-invalid-http-409.md`](../migrations/sync-scope-invalid-http-409.md).
