# ADR-004: Dark Mode via Token-Layer Inversion (no `dark:` variant sweep)

## Context

iKuck ships a light-only PWA (React/Vite/Tailwind 3.4 + `--ik-*` CSS tokens in
`frontend/src/index.css`). The user requested a production dark mode within 8
hours, with every action tracked on a dedicated Kanban board
(`ikuck-dark-mode`) and all decisions taken autonomously.

Measured state of the codebase at decision time:

- **No theme infrastructure**: no `prefers-color-scheme`, no `data-theme`
  attribute, no theme persistence (only the analogous
  `src/domain/motionPreference.ts` → `localStorage['ikuck-motion-preference']`
  → `html[data-motion]` pattern).
- **464 default-Tailwind-palette utility usages** across 33 files
  (`bg-white` ×122, `gray-*` ×417…, `emerald-*`, `amber-*`, `rose-*`,
  `red-*`), including opacity modifiers (`bg-white/70`, `emerald-50/70`).
- Custom palette entries (`porcelain`, `ink`, `basil`, `tomato`, `yolk`,
  `sage`) in `tailwind.config.js`, but only 2 utility usages
  (`text-ink`, `bg-sage`); brand styling otherwise flows through `.ik-*`
  classes consuming `--ik-*` tokens.
- ~19 hex literals inside `index.css` (e.g. `#f8cf69`, `#8a5700`) and 2
  arbitrary values in TSX.
- PWA surface: `index.html` `<meta name="theme-color" content="#247A4A">`
  and `vite.config.ts` manifest `theme_color: '#247A4A'`,
  `background_color: '#FAFBF7'`.

Constraints: 8-hour deadline; light mode must not regress (761-test suite +
E2E + axe currently green); guest-first/offline PWA (theme is client-only, no
backend contract); DESIGN.md semantics (ink/porcelain/basil/sage/yolk/tomato)
must survive the flip.

## Decision

**Invert the token layer, not the components.** Dark mode = one attribute on
`<html>` (`data-theme="dark"`) that redefines color variables; components
stay untouched.

1. **Tailwind palette → CSS-variable indirection.** In `tailwind.config.js`,
   every *used* default-palette color is redefined as
   `'rgb(var(--tk-<name>) / <alpha-value>)'` (the documented Tailwind v3
   alpha-capable variable pattern). `--tk-*` channel triplets are declared in
   `index.css` `:root` with the **exact current Tailwind hex values**, so
   light mode is bit-identical, and overridden under
   `html[data-theme='dark']`. Opacity modifiers keep working because
   `<alpha-value>` is resolved by Tailwind at build time.
2. **`--ik-*` semantic tokens** (used by `.ik-*` classes, `::selection`,
   shadows, focus ring) get a parallel dark override block in the same
   selector. Light values untouched.
3. **Theme preference module** `src/domain/colorTheme.ts` mirrors the
   proven `motionPreference.ts` pattern: `localStorage['ikuck-color-theme']`
   ∈ {`light`,`dark`,`system`}, `applyColorTheme()` sets
   `document.documentElement.dataset.theme`, `matchMedia('(prefers-color-scheme: dark)')`
   listener for `system`, never throws (storage-disabled fallback to
   `system`). A 3-line inline script in `index.html <head>` applies the stored
   theme **before first paint** (FOUC-free), and `<meta name="theme-color">`
   is updated at runtime (light `#247A4A`, dark page tone).
4. **Palette seed values** are generated by HSL lightness inversion (hue
   preserved, neutrals desaturated, range compressed to [6%, 96%] to avoid
   pure `#000`/`#fff`), then hand-tuned against axe contrast results. Every
   `fg/bg` pair flips *together*, so contrast relationships are preserved by
   construction (verified for the hot pairs: body text 8.6:1, chips 6.9–9.9:1,
   hover rows 11.1:1).
5. **Three-way UI switch** (Chiaro / Scuro / Sistema, default `system`) in
   Profile next to the existing motion preference, plus a quick toggle in the
   app header. UI copy Italian, code/comments English.

## Alternatives Considered

- **`darkMode: 'class'` + `dark:` variant sweep across 464 sites** —
  rejected: massive diff in 33 files, high regression risk under the 8h
  budget, every future component must remember the variants, and review
  burden is unbounded. Also would *not* cover the `.ik-*`/`--ik-*` layer,
  so two systems would have to be maintained forever.
- **CSS-only `prefers-color-scheme` with no user override** — rejected: no
  way to pin light/dark, no visible control, user asked for a switchable
  feature and PWA users expect explicit control.
- **Backend-persisted preference (user profile column)** — rejected: theme is
  presentation state; guest-first architecture keeps device preferences
  local (same as motion); a DB column + contract + sync would spend backend
  budget with zero UX gain inside the 8h window.
- **CSS-in-JS runtime theming / styled-components** — rejected: introduces a
  second styling system beside Tailwind + tokens; bundle and perf cost.
- **Auto-invert with `filter: invert(1)` hacks** — rejected: breaks images,
  brand identity, and accessibility.

## Consequences

- **Backend / DB / contracts:** none. No Drizzle migration, no
  `shared/src/contracts.ts` change, no API endpoints.
- **Frontend:** `tailwind.config.js` rewritten to variable-backed colors;
  `index.css` gains `:root` triplets + `html[data-theme='dark']` overrides +
  `color-scheme: dark` (native controls/scrollbars); new
  `src/domain/colorTheme.ts` (+ tests); `main.tsx` applies theme;
  `index.html` gets the pre-paint script and dynamic `theme-color`;
  Profile + header gain the switch. Known traps called out in the tech spec
  (yolk-on-ink pairs, `::selection`, action-panel yolk buttons, stray hex
  literals → promoted to tokens).
- **Testing:** new unit tests (colorTheme, mirroring the storage-throw case),
  a guard test forbidding new hardcoded colors in TSX, E2E scenarios for
  toggle/persistence/system mode, axe runs in both themes, full existing
  suite must stay green (light-mode regression gate).
- **Deploy:** frontend-only release — version bump, tag, standalone deploy,
  post-deploy verification on the public origin. No Compose env changes, no
  migrations. Workbox precache invalidates automatically via `version.json`.
- **Performance:** zero runtime cost beyond one `matchMedia` listener and a
  `localStorage` read; variables resolve at paint, no JS-driven restyling.
- **Risk:** saturated accent steps become lighter in dark mode (e.g.
  `emerald-700` buttons); accepted, mitigated by contrast gates and visual
  tuning; any pair that fails axe is hand-adjusted in the token block only.
