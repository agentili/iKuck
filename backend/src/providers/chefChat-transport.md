# Chef chat transport integration contract

`startChat(request)` synchronously starts at most one fetch and returns `{ response, settled }`. `response` is the existing sanitized client result, including timeout; `settled` never rejects and resolves only after the fetch promise and the body consumer have settled, including late fetch/body success or failure and awaited stream cancellation. A pre-dispatch validation/configuration failure or already-aborted signal performs no fetch and settles. A non-cooperative operation may keep `settled` pending forever. `chat()` preserves the old response-only API and must not be used as a concurrency-gate lifetime signal.

The route must validate and check consent, reserve quota and acquire **both** user and global gates before starting the operation. Attach ownership of both gates to that particular operation synchronously, immediately consume `response` for the HTTP reply (504 on provider timeout), and release gates only after `settled`, using token-checked, idempotent release. Never await `settled` before returning the timeout to the client. Capture release failures, retain/mark ownership uncertain and fail closed; never drop an unhandled response or release rejection. Account for dispatch according to the quota policy even if the client disconnects. Prevent a new dispatch if gate acquisition, durable ownership, Redis, or renewal cannot be confirmed. This is an integration requirement, not implemented by the adapter.

`settled` describes only JavaScript-visible completion of fetch and body operations, including rejection; it is not proof that sockets or a remote provider have ceased processing. A rejected stream cancellation or fetch rejection can leave underlying work unobservable. Abort, HTTP timeout, process death, and Redis lease expiry likewise prove no such thing. No strict provider-side concurrency guarantee is possible from this signal alone.

For process crashes, partitions, lost Redis writes, and uncertain releases, do not let a TTL automatically authorize replacement work: persist an ownership/uncertainty record in an appropriately durable, consistently coordinated store and quarantine affected user and global capacity across restart; reject new work until reconciliation can prove safety. Redis TTL may detect stale owners but must not clear uncertainty or reopen a gate. Redis restart/data loss requires fail-closed recovery, including global quarantine if ownership cannot be reconstructed; fencing protects state updates but cannot stop an already dispatched provider request. Manual reconciliation or an externally enforced provider/transport bound and verified termination mechanism are needed to restore capacity safely. If that evidence is unavailable, the safe result is indefinite unavailability; neither arbitrary grace periods nor lease renewal prove cessation. Durable coordination and operational reconciliation are future quota/route work, not guarantees delivered here.
